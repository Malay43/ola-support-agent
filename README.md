# Ola Domain Support Agent (CrewAI + Autogen review + FastAPI)

**Track completed: Ola (Business Operations / Customer Support)**  - domain `Support`.

Everything in this repository runs under `MOCK_LLM` (the default) with **zero API keys and zero network access** after the
one-time download of the free SentenceTransformers model (`sentence-transformers/all-MiniLM-L6-v2`). Embedder used for the numbers below: **sentence-transformers/all-MiniLM-L6-v2**.

**Telemetry:** I set `CREWAI_DISABLE_TELEMETRY=true`, `OTEL_SDK_DISABLED=true` (plus `CREWAI_TRACING_ENABLED=false`,
`ANONYMIZED_TELEMETRY=False` for ChromaDB) in `config.py`, which every entry point imports *before* `crewai`/`chromadb`, so
`crew.kickoff()` makes no outbound call. (`run_all.py` prints their values at the start of the run.)

The knowledge-base policies are **fictional and illustrative**, written for this project; they are not Ola's real internal policies.

## How to run

```bash
bash setup.sh                  # venv + pinned dependencies (Windows: .\setup.ps1; see protobuf note inside)
source venv/bin/activate   # Windows: venv\Scripts\Activate.ps1
python run_all.py              # runs every task's demo, writes transcripts/*.txt (about a minute)
python make_readme.py          # regenerates this README from the real numbers
uvicorn app:app --port 8000    # optional: serve the API (POST /ask, POST /add-document, WS /ws/chat)
pytest -q                      # optional: unit tests
```

## Part 1 - Dataset design and RAG core

### Task 1 - dataset design choices (reproducible)

- `random.Random(SEED)` is the only randomness source: **SEED = 13**, **N = 60** records, generated by `dataset.py`.
- Category weights `{'Billing': 0.26, 'Technical Issue': 0.24, 'Account Access': 0.18, 'Product Defect': 0.14, 'General Inquiry': 0.18}`
- Status weights `{'Open': 0.18, 'In Progress': 0.2, 'Escalated': 0.14, 'Resolved': 0.28, 'Closed': 0.2}`
- `escalated = True` for every ticket in status `Escalated`, otherwise with probability 0.06.
- **Amount range** (`resolution_time_hours`): lognormal around a per-category median {'Billing': 10.0, 'Technical Issue': 24.0, 'Account Access': 4.0, 'Product Defect': 48.0, 'General Inquiry': 2.0}, clamped to
  (0.5, 96.0) hours - quick inquiries and account-access issues close in minutes to hours, billing in about a working day, and
  product defects take days; 96 h is the P4 SLA ceiling. For unresolved tickets it is the hours elapsed so far.
- `days_since_created` is uniform on 0-30.
- No record was hand-edited; seed 13 was chosen from a seed sweep for a balanced draw.

Counts per category: `{'Billing': 14, 'Account Access': 11, 'General Inquiry': 12, 'Product Defect': 10, 'Technical Issue': 13}`  
Counts per status: `{'Resolved': 20, 'Closed': 10, 'In Progress': 14, 'Escalated': 10, 'Open': 6}`  
`escalated=True`: **18.3%** (required band 10-30%).

### Tasks 2-3 - knowledge base and the two ChromaDB collections

12 documents in `kb_docs.py` (4-5 sentences each) cover all 12 required topics. Chunking: fixed-size
(320 chars, 80 overlap, word-boundary snapped) and sentence-based; each strategy is embedded and
`upsert`ed into its own collection: **fixed = 24 chunks, sentence = 53 chunks**.

## Part 2 - CrewAI orchestration

### Task 6 - `check_support_ticket_status` and the designed escalation score

escalation_score = 0.6 * escalated + 0.4 * (days_since_created / 30), always in [0, 1]. Recommend escalation when score >= 0.39: this is the 80th percentile of the scores over my 60 generated tickets, so 11 of 60 tickets (18%) are above it, i.e. only the top fifth of the queue is escalated. In practice every ticket already flagged `escalated` (score >= 0.6) is recommended for escalation, and an unflagged ticket is recommended only when it is at least 30 days old.

### Task 7 - the crew (`.kickoff()`)

Retrieval Agent (holds `rag_lookup`), Lookup Agent (holds `check_support_ticket_status`), Response Composer (no tools). Tool invocations per query:

- `How fast must we reply to a P1 ticket?` -> `rag_lookup` x1, `check_support_ticket_status` x0
- `What is the status of ticket TKT-0003?` -> `rag_lookup` x0, `check_support_ticket_status` x1
- `Ticket TKT-0010: when does an agent need Tier 2 approval for a refund, and should it be escalated?` -> `rag_lookup` x1, `check_support_ticket_status` x1

### Tasks 8-10 - memory, structured output, guardrails

- **Memory:** `RunnableWithMessageHistory` over `InMemoryChatMessageHistory` (the expected `LangChainDeprecationWarning` is left visible). In
  `transcripts/part2_task8_memory.txt`, "Should it be escalated?" resolves to `TKT-0003` from the earlier turn, while the same sentence in a fresh session asks for a ticket id.
- **Schema:** every crew response is a `SupportAnswer` (Pydantic, `output_pydantic=` on the Composer task) and is re-validated in code; an invalid payload is shown being rejected.
- **Guardrails:** phone-number masking (several formats; ticket ids and ordinary numbers are untouched), regex prompt-injection detection, and an output groundedness guard that refuses
  answers without single-sentence support in the retrieved context. Each is demonstrated firing in `transcripts/part2_task10_guardrails.txt`.
  Rider/driver name, address and payment details are free text and out of scope for the keyless masker (only fabricated examples are used).

## Part 4 - Resilience and governance

- **Task 14:** `RoundRobinGroupChat([Policy_Compliance_Reviewer, Final_Editor], max_turns=2, custom_message_types=[StructuredMessage[ReviewVerdict]])`, editor has `output_content_type=ReviewVerdict`
  (`approved`, `final_answer`, `reason`). Clean draft -> `approved=True` unchanged; draft with an injected claim -> `approved=False`, claim removed (`Removed 1 unsupported claim(s): Refunds above 5,000 rupees are paid instantly in cash....`).
- **Task 15 - application layer:** `make_agent()` calls `assert_tool_allowed(role, tool)` before building any agent, so only the Lookup Agent can hold `check_support_ticket_status`; wiring it to the Retrieval Agent
  or Composer raises `PermissionError` (shown in the transcript). **Risk class: Medium.** I classify this system as MEDIUM risk. It is a customer-support assistant that answers policy questions and reads ticket status, which the scheme lists under 'customer support tickets' (Medium), not under summarisation (Low). It is not High: it handles no medical data, makes no hiring decision and touches no financial account - it cannot issue refunds or change a ticket, it only reads one record and quotes policy. The residual risks are a wrong or ungrounded answer and leakage of a phone number, and both are controlled by the retrieval-similarity groundedness gate, the Autogen review stage, input-side PII masking (also applied before logging), prompt-injection detection, a per-request token budget, and a read-only tool that only the Lookup Agent may hold.
- **Task 15 - runtime layer:** per-request budget of 6000 tokens ($0.0120); a normal request used 3437 tokens, a ~30k-character request is rejected up front, and a
  deliberately tight cap is enforced mid-request.
- **Task 16:** in-memory cache keyed by normalized query text. Repeated query: miss 10.58 ms (1 retrieval + 1 generation call) -> hit 0.01 ms
  (+0 retrieval, +0 generation calls), with different casing/punctuation hitting the same key.

## Notes on the MOCK_LLM implementation (the two silent pitfalls in the brief)

`MockCrewLLM` extends `crewai.llms.base_llm.BaseLLM`. (1) It never searches the whole conversation for `Observation:` (CrewAI's own system prompt contains that text); it only inspects assistant messages.
(2) It chooses a tool from the tool's declared argument schema (`record_id` vs `query`), never from its name. `tests/test_core.py` covers both.
